# Контракт воркера

Все типы воркеров ведут себя одинаково. Этот контракт проверяют тесты `tests/contract/`, которые запускают один и тот же набор проверок для каждого типа.

---

## Авторизация

- Каждый запрос, кроме `OPTIONS`, должен содержать заголовок `X-Proxyflare-Key` со значением секрета `PROXYFLARE_KEY`
- Без верного ключа воркер отвечает `401` и ничего не запрашивает у целевого сайта
- Если секрет не задан, отклоняются все запросы
- `pf create` генерирует отдельный ключ для каждого воркера и сохраняет его в файл воркеров

## Целевой URL

Источники по убыванию приоритета:

| Источник | Пример |
|----------|--------|
| Query-параметр | `/?url=https%3A%2F%2Fexample.com%2Fa` |
| Заголовок | `X-Target-URL: https://example.com/a` |
| Путь | `/https://example.com/a` |

- Разрешены только схемы `http` и `https`
- Нет цели или она некорректна: `400`

## Query целевого URL

- Собственный query цели сохраняется полностью, включая её параметры `url`, `_cb` и `_t`
- Остальные параметры запроса к воркеру добавляются к цели. Поэтому работают запись через путь и незакодированный `?url=https://example.com/?a=1&b=2`
- Параметры запроса к воркеру `url`, `_cb` и `_t` не передаются

💡 Клиентская библиотека всегда кодирует цель в `?url=`, поэтому эти правила её не затрагивают.

## Заголовки запроса

Передаются цели все заголовки, кроме:

- `Host`
- служебных: `X-Proxyflare-Key`, `X-Target-URL`, `X-My-X-Forwarded-For`
- раскрывающих клиента: `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host`, `X-Real-IP`, все `CF-*`
- hop-by-hop: `Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailer`, `Transfer-Encoding`, `Upgrade`, а также `Content-Length`

`X-Forwarded-For` задаётся заново: значением `X-My-X-Forwarded-For`, если он есть, иначе случайным IPv4 с октетами 1–255.

⚠️ Cloudflare сам добавляет к исходящим запросам заголовок `CF-Worker` с именем воркера или поддоменом. Воркер не может его убрать, так что сайт видит, что запрос пришёл через Workers.

## Ответ

- Статус, тело и заголовки передаются без изменений, включая несколько `Set-Cookie`
- Удаляются `Content-Encoding`, `Content-Length` и `Transfer-Encoding` ответа цели: воркер получает тело уже распакованным. Рантайм может снова сжать его для клиента, если тот поддерживает сжатие
- Редиректы цели воркер проходит сам
- Ко всем ответам добавляются CORS-заголовки

## Ошибки воркера

Ошибка самого воркера:

- имеет заголовок `X-Proxyflare-Error: true`, который отличает её от ответа сайта с тем же статусом
- содержит JSON вида `{"error": "..."}` без внутренних подробностей

| Статус | Когда |
|--------|-------|
| `400` | Нет цели, она некорректна или схема не `http`/`https` |
| `401` | Нет ключа или он неверный |
| `502` | Запрос к цели не удался |

## CORS

- `OPTIONS` отвечает `204` без проверки ключа: браузер не отправляет свои заголовки в preflight-запросе
- `Access-Control-Allow-Origin: *`
- `Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS, PATCH, HEAD`
- `Access-Control-Allow-Headers: *`
